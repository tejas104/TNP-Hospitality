Findings
1. [Confirmed — blocking] Fixed PreviewControls overlay makes primary-action buttons unclickable at the bottom of pages on mobile (390×844)
components/tnp/shared/PreviewControls.tsx renders two position: fixed elements globally (mounted in AppShell.tsx): .preview-notice (z-index 950) and .preview-control-panel (z-index 42). On mobile these expand to near full-width and together occupy roughly 150–200px of permanent screen height at the bottom of the viewport, with no reserved padding on the underlying page content.

Reproduced concretely with elementFromPoint hit-testing after a real (mouse-wheel) scroll to the bottom of the page:

/client — the "Submit Requirement" button (the last element on the page) resolves to <div class="preview-notice"> at its center point, not the button. It is not clickable in this state, and since this is the maximum scroll position, there is no way to scroll it clear.
/freelancer — the "Show Sample Scan Result" button resolves to the preview-controls <output> element at its center point — also unclickable.
At 1440×900 the same buttons are not blocked (the overlay sits in the corners, clear of centered content) — this is mobile-viewport-specific.
/planner's "Submit Requirement" is reachable mid-scroll (not blocked), but the final status-timeline steps ("Team Confirmed", "Completed") are visually obscured at the true bottom of that page too.
This is new code from this diff (both files are new/S1-owned; the mount point in AppShell.tsx is a new S1 edit), not an inherited defect. docs/DESIGN.md states "No dead primary actions... earn readiness credit", and the S1 contract explicitly requires 390×844 browser evidence covering "preview-controls reset/reload/focus" and "five-route smoke" — a full check at that viewport would have caught this.

Suggested fix (stays within S1-owned files): reduce the panel's mobile footprint / reposition it away from primary CTA position, or reserve bottom padding on page content equal to the overlay height, or make pointer-events scoped only to the panel's actual visible controls. This does not require touching S0-frozen globals.css — it can be done entirely inside PreviewControls.tsx's own scoped <style> block.

2. [Confirmed — non-blocking, should be tracked] listPayouts(workerId, …) silently ignores its workerId filter
lib/contracts/preview.ts declares listPayouts(workerId?: string, options?: QueryOptions), and lib/demo/service.ts implements it as listPayouts(_workerId?: string, options?: QueryOptions) { return this.query('payouts', options, (r) => page(r.payouts), page([])); } — the parameter is accepted but never used to filter; it always returns every payout. This is untested (the test suite calls listPayouts() with no argument). Unlike listEarnings/listAssignments, which do filter correctly by workerId, this is an inconsistency.

Note the Payout type itself doesn't carry a workerId (only earningIds), so a correct fix requires either deriving worker scope via earnings, or an explicit decision that payouts are month-level aggregates not meant to be worker-scoped (in which case the parameter should be removed from the interface, not silently ignored). Flagging this now so a D-03 consumer doesn't build a "my payouts" view on top of a signature that quietly returns everyone's data.
