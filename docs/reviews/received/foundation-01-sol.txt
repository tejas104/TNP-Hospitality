## Findings

### [P1 / blocking] 1. The exported mutation contract accepts any operation and payload and returns unknown

Evidence:

- lib/contracts/preview.ts:24-30 defines a generic MutationRequest<Operation extends string, Payload> with no operation-to-payload/result mapping.
- lib/contracts/preview.ts:307 exposes only mutate<Operation extends string, Payload>(...): Promise<PreviewOutcome<unknown>> instead of typed operations/outcomes for the consumer matrix.
- lib/demo/service.ts:31-55 lists operation-name constants, but those constants are not connected to payload and result types.
- lib/demo/service.ts:196-198 casts the request back to MutationRequest<string, unknown> and dispatches at runtime.
- External compile probe: TypeScript accepted operation: 'this-operation-does-not-exist' with an arbitrary payload against PreviewService; tsc exited 0.

Impact: dependent consumers cannot discover or verify required fields, payload shapes, or success values at compile time. Typos and wrong payloads compile, while successful values require unsafe narrowing/casts. This does not satisfy S1's requirement that every consumer operation have a usable Promise-based typed outcome before the contract freeze.

### [P1 / blocking] 2. A declined assignment can be reactivated past capacity and without overlap/eligibility revalidation

Evidence:

- lib/demo/service.ts:91-103 excludes not-coming assignments from capacity and overlap reservations.
- lib/demo/service.ts:323-338 correctly checks duplicate allocation, eligibility, capacity, and overlap when creating an assignment.
- lib/demo/service.ts:341-348 later changes any assignment to coming without checking allocation state, capacity, eligibility, or overlap.
- Targeted probe: with position quantity set to 2, one worker declined, another worker filled the released slot, and the original worker then responded coming. The service returned SUCCESS and left 3 counted active assignments for quantity 2.
- tests/preview-contract.test.mjs:150-180 is titled capacity-safe/atomic, but toggles coming then not-coming before another fill and never tests a not-coming -> coming response after the slot is reused. The suite contains no assertion for an OVERLAP rejection.

Impact: the preview can show an overfilled or overlapping roster even though its allocation entry point is safe. Because consumer UIs will share this foundation, the defect undermines the exact capacity/overlap/replacement behavior the preview is meant to demonstrate. This is a simulation correctness failure; it does not claim or require production concurrency.

### [P1 / blocking] 3. Attendance accepts an ineligible assignment state and creates/retains payable earnings from unverified or absent attendance

Evidence:

- lib/demo/service.ts:376-385 validates token/event/expiry/duplicate scan and evidence-state syntax, but does not require an active eligible assignment with a coming response. A pass remains usable after markNonresponse or replacement.
- lib/demo/service.ts:387-399 creates a full-rate earning for every accepted attendance, including gps-denied, gps-missing, and outside-radius exception states.
- lib/demo/service.ts:404-414 can correct attendance to absent but does not update, reverse, or invalidate the associated earning.
- lib/contracts/preview.ts:134-142 stores no assignment rate snapshot; lib/demo/service.ts:388-395 derives the earning from the current position rate instead.
- Targeted probe: an admin assignment was marked not-coming; its pass still recorded gps-missing attendance successfully, created a 250000 paise earning, and correction to absent left the earning at 250000 paise.
- tests/preview-contract.test.mjs:138-147 explicitly asserts that gps-missing exception attendance creates a full 250000 paise earning, so the passing suite currently certifies the wrong money invariant.

Impact: the preview can present earnings that are not derived from an effective verified attendance result and can retain money after the effective result becomes absent. This conflicts with the domain rules and makes the C-03/D-02/D-03 shared scenario unsafe for consumer implementation.

### [P1 / blocking] 4. Worker payout history is not worker-scoped

Evidence:

- lib/contracts/preview.ts:302 advertises listPayouts(workerId?: string, ...).
- lib/contracts/preview.ts:180-186 gives Payout no worker ID; it can only be related through earningIds.
- lib/demo/service.ts:181 names the argument _workerId and always returns every payout.
- Targeted probe: listPayouts('tnp-demo-worker-004') for a worker with no earnings returned all 5 payouts, the same count as unfiltered listPayouts().

Impact: C-03 cannot consume the contract to show a worker's payout history without receiving unrelated workers' payout states. The operation exists syntactically but is not usable as specified.

### [P2] 5. The required distinct preview approval evidence is absent

Evidence:

- lib/demo/service.ts:509-521 records each approval actor in audit entries but does not retain/compare approval actors on the earning.
- tests/preview-contract.test.mjs:13-14 defaults every mutation to actor tnp-test-actor.
- tests/preview-contract.test.mjs:237-240 uses that same default actor for supervisor and Finance approvals.

Impact: the suite does not meet the explicit S1 test requirement for two distinct preview approvals. DEC-16 leaves production separation-of-duties policy pending, so this finding does not demand production authorization enforcement; the preview test and labelled scenario still need two distinct sample actors as specified.

### [P3] 6. One visible Operations navigation label still presents a live-state claim

Evidence:

- components/tnp/portals/operations/AdminOperations.tsx:24 visibly labels the sidebar item Live Workforce.
- The destination section itself is labelled SAMPLE EVENT OPERATIONS at components/tnp/portals/operations/AdminOperations.tsx:83, and the global warning is correct, so the issue is localized.

Impact: the residual label weakens the otherwise clear preview-only copy by suggesting real-time workforce tracking. It should use sample/demo wording before the truthful-preview gate passes.
